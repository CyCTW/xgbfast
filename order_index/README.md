# order_index：策略自有掛單的價位索引

這個目錄是獨立的 header-only C++20 範例，和 xgbfast 函式庫無關，也不會被 xgbfast 的 build 或 CI 編到。

## 設計

- 價格一律用整數 tick 表示。
- 每一邊（買或賣）用一個**雙端排序陣列**，資料從中間開始放，兩端都留空間：
  - 新的最佳價（積極回補）放到尾端，O(1)
  - 新的最差價（遠端被動單）放到頭端，O(1)
  - 插在中間時，往比較近的一端 memmove
- 內部以 key 排序：買方 `key = px`，賣方 `key = -px`，所以最佳價永遠在尾端。
- `PriceLevel` 放在固定容量的 pool 裡。`levelId` 不會因為陣列搬移而改變，訂單可以直接存它。
- hot path 不配置記憶體、不丟例外。容量滿時 `addOrder` 回傳 `false`，由呼叫端決定要不要拒單。
- 查找時，價位數 ≤ 32 用線性掃描（從最佳價端開始），超過改用二分搜尋。
- **空價位延遲回收**（`SideIndex<Side, Cap, MaxEmpty>`）：
  - 價位的訂單數歸零時先不回收，因為刪單後常常馬上在同價位重下。
  - 不變式：**陣列兩端一定是有掛單的價位**。端點清空時會連同相鄰的空價位一起回收，所以 `bestPx()` 和 `worstPx()` 仍是 O(1)。
  - 空價位超過 `MaxEmpty` 個，或容量已滿又需要新價位時，做一次 O(n) 壓縮。呼叫端也可以在空閒時間呼叫 `purgeEmpty()`，把這個成本移出 hot path。
  - `MaxEmpty = 0` 等同立即回收。
- **每個價位的 FIFO 訂單佇列**（`OrderSide<Side, LevelCap, OrderCap, MaxEmpty>`）：
  - 訂單放在固定容量的池中，handle 在訂單存活期間不變，可以編進 clOrdId。
  - 每個價位的訂單用侵入式雙向鏈結串起來，`PriceLevel` 裡存 `head`/`tail`。
  - 排隊優先權：成交和減量保留原位置，加量排到隊尾，改價移到新價位的隊尾。
  - 改價時先建立新價位，再離開舊價位，所以失敗時狀態完全不變。例外是價位容量全滿、但舊價位只剩這張單：這時先離開舊價位騰出空間，一定成功。
  - `qtyAhead(h)` 回傳排在這張單前面的量，`bestFront()` 回傳最佳價隊首。

## fuzz 涵蓋的內容

- 事件分布：90% 的價位落在 mid ± 20 tick，5% 是積極價，5% 是遠端被動價。極端價位傾向很快被移除，mid 偶爾會跳空。
- 容量分成 8、48、256 三種：8 會頻繁撞到兩端和容量上限，48 橫跨線性掃描和二分搜尋的切換點。
- 每一步之後檢查：內部不變式（嚴格排序、pool 使用量等於價位數、`head ≤ tail`）、最佳價、最差價、最佳到最差的完整走訪（價格、量、單數），以及存在和不存在價位的精確查找。
- `SideIndex` 另外用 `MaxEmpty` = 0、3、8、32 測試延遲回收，並隨機插入空閒時的 `purgeEmpty()`。

`OrderSide` 的 fuzz 事件包含：新單、最佳價隊首成交、隨機部分成交、刪單、同價改量（加量或減量）、改價（含改到極端價位），以及 mid 跳空。組態刻意讓價位容量和訂單池分別成為瓶頸。每一步之後比對：

- 內部不變式：鏈結的前後指標一致、每個價位的量和單數彙總等於鏈結內容
- 價位彙總
- **每個價位的 FIFO 順序**（handle、clOrdId、剩餘量）
- `qtyAhead`
- `bestFront`
- 容量不足時的拒絕條件

我也刻意在程式裡注入過幾種錯誤來確認測試抓得到，例如加量不排到隊尾、端點空價位沒回收、重新啟用空價位時計數沒減、unlink 沒更新 tail、`find` 回傳空價位等，每一種都會被測試抓到。

`BackSortedIndex` 和 `SideIndex` 的 API、延遲回收語意都相同，所以兩組 fuzz、所有確定性測試（只檢查雙端配置的那一項除外）和 `OrderSide`（透過 `IndexT` 模板參數）都會各跑一次這兩種實作。

## 雙端 vs 單端（原方案一）vs `std::map`

兩種陣列實作只差在**陣列配置**，其他行為完全相同，所以測出來的差異只來自配置。

| | 雙端（`SideIndex`） | 單端（`BackSortedIndex`） |
|---|---|---|
| 新的最佳價 | O(1) | O(1) |
| 新的最差價 | O(1) | O(n)，整段往右搬 |
| 中間插入 / 刪除 | 往比較近的一端搬，平均約 n/4 | 往右端搬，平均約 n/2 |
| 最差端清空 | O(1) | O(n)，整段往左搬 |
| 額外成本 | 某一端空間用完時要整段移回中間 | 無 |
| 程式複雜度 | 較高：recenter 的邊界條件曾經出過 bug，被 fuzz 抓到 | 較低 |
| 記憶體 | 相同 | 相同 |

### 實測

- 環境：x86-64 雲端 VM，綁核心，容量 1024，`MaxEmpty=8`，每個工作負載 100 萬次操作。
- 每次操作都會查一次最佳價。
- 單位是 ns。p99/p99.9 是 3 次逐筆計時中各百分位的最小值，已扣除計時器開銷。
- 下表數字取兩次完整執行中較具代表性的一次，兩次之間約有 ±10% 的差異。
- 執行 `make bench` 可以看完整結果（含 p99.99）。

| 工作負載 | L | 雙端 mean / p99 / p99.9 | 單端 mean / p99 / p99.9 | map mean / p99 / p99.9 |
|---|---|---|---|---|
| near（隨機） | 8 | 26 / 84 / 302 | 28 / 90 / 332 | 40 / 97 / 363 |
| near（隨機） | 128 | 60 / 262 / 407 | 63 / 253 / 404 | 61 / 126 / 406 |
| mixed（90/5/5） | 32 | 42 / 167 / 351 | 45 / 174 / 362 | 51 / 120 / 385 |
| deep-churn | 128 | 51 / 251 / 408 | 46 / 262 / 419 | 56 / 125 / 365 |
| **requeue** | 8 | **5 / 15 / 30** | 10 / 22 / 170 | 19 / 36 / 117 |
| **requeue** | 32 | **5 / 13 / 26** | 17 / 58 / 225 | 23 / 53 / 153 |
| **requeue** | 128 | **7 / 17 / 38** | 18 / 38 / 191 | 25 / 59 / 100 |

工作負載說明：

- **near / mixed / deep-churn / aggr-churn**：價位隨機新增和移除，其中一部分是很快就被移除的極端價位。
- **requeue**：模擬做市。最佳價成交後，在目前最差價的下一檔補一張，所以**每次操作都是「最佳端刪除 + 最差端新增」**。

### 結論

1. **價位隨機進出的情況下，雙端和單端差不多**。兩者差距在 ±10% 的雜訊內，而且誰快誰慢會互換，連我原本預期單端會吃虧的 deep-churn 也一樣。原因是 128 個價位的 memmove 最多只有 2KB，在 L1 快取裡只要幾十 ns；而且只有部分操作會觸發搬移，真正主導成本的是隨機位置的查找。
2. **在最差端頻繁新增或刪除時，雙端明顯比較好**（requeue）：平均快 2 到 3 倍，p99.9 約 30–40 ns，單端約 170–225 ns。做市時「成交後往後補單」、階梯單整體平移，或是回補時常把單掛到最差端，都是這種模式。
3. **`std::map` 在價位多時 p99 最好**。L≥32 時 map 的 p99 約 120 ns，兩種陣列約 170–260 ns，因為陣列每次價位結構改變都要 memmove，而 map 每次操作的成本比較平均。不過 map 在價位少時平均比較慢（L=8 時 40 vs 26），也會在 hot path 上配置記憶體（malloc）。
4. **`MaxEmpty` 是 p99 和 p99.9 之間的取捨**（見 `make bench` 最後一段，L=128）：
   - `MaxEmpty=0`（立即回收）：平均最慢（約 85）。
   - `MaxEmpty=8`：平均約 60，p99 約 260。
   - `MaxEmpty=64`：p99 降到約 110–140，跟 map 同一級；但累積的空價位一次壓縮時，p99.9 會升到約 800。

   如果能在策略空閒時呼叫 `purgeEmpty()`，理論上可以兼顧兩者：用大的 `MaxEmpty` 把 p99 壓低，壓縮成本則移到空閒時間。這一點還沒有實測。

### 建議

- **預設用雙端**。它在隨機工作負載下不輸單端，在最差端頻繁進出的情況下明顯勝出，多出來的複雜度已經有 fuzz 覆蓋。
- 如果確定價位幾乎只在最佳端附近進出，而且想要最簡單的程式，單端也可以，兩者效能差不多。
- 如果常態價位數 ≥ 32，而且 p99 比平均重要，可以加大 `MaxEmpty`，並在空閒時呼叫 `purgeEmpty()`。
